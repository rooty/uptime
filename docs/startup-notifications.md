# Уведомления о запуске приложения

## Обзор

После успешной привязки HTTP-порта Local Ops Board отправляет в Telegram сообщение
**СЕРВИС ЗАПУЩЕН**. Вы получаете его после обычного перезапуска и после установки нового релиза.
Сообщение содержит версию, commit, время сборки, время запуска в UTC и адрес HTTP listener.

Это сообщение подтверждает запуск процесса и его HTTP listener, а не успешное завершение всех этапов
GitHub Actions, доступность внешнего домена или исправность мониторируемых сервисов.
Приложение не добавляет отдельное сообщение из workflow, поэтому один запуск не создаёт два сообщения.

## Требования

- Включите Telegram в настройках уведомлений `/uptime/settings`.
- Настройте Bot token и Chat ID существующего канала приложения.
- Разрешите серверу исходящий HTTPS-доступ к `api.telegram.org`.
- Для отображения версии релиза используйте стандартную release-сборку с `VERSION`, `COMMIT` и `BUILD_TIME`.
  При локальном запуске без этих значений вы видите `dev` и `unknown`.

Текущий диалог с AI-агентом не настраивает доступ приложения к Telegram.
Приложение использует только бота и чат из собственных настроек, а не учётные данные агента.
Не отправляйте Bot token в чат и не добавляйте его в репозиторий.

## Шаги

1. Откройте `/uptime/settings`, включите Telegram, задайте Bot token и Chat ID в интерфейсе приложения.
2. Нажмите **Сохранить и проверить**, чтобы проверить существующую отправку тестовых уведомлений.
3. После следующего согласованного запуска приложения проверьте сообщение **СЕРВИС ЗАПУЩЕН**
   в настроенном чате. Сверьте commit с устанавливаемым релизом.
4. Если вы перезапускаете ту же версию, приложение снова отправляет одно сообщение с тем же commit
   и новым временем запуска. Периодические health-check запросы не создают эти сообщения.
5. Для отключения отправки выключите Telegram и сохраните настройки.
   Этот переключатель также отключает остальные Telegram-уведомления приложения.

Событие сохраняется в существующей истории уведомлений с типом `application_started` и `service_id=0`.
Его наличие в истории само по себе не подтверждает доставку: Telegram может вернуть ошибку.
Новые таблицы, настройки и переменные окружения не требуются.
В Slack и Email уведомление о запуске не отправляется.

Отправка выполняется отдельно от обработки HTTP-запросов, с таймаутом `10` секунд.
Приложение выполняет одну попытку без автоматического повтора, чтобы не создавать дубли при неоднозначной
сетевой ошибке. Ошибка доставки не останавливает сервер и не меняет статусы мониторируемых сервисов.

## Решение проблем

- **Сообщение не пришло.** Убедитесь, что Telegram включён и Bot token и Chat ID сохранены.
  Включение канала после запуска не создаёт задним числом уведомление о предыдущем старте.
- **Порт занят.** Приложение не отправляет сообщение о запуске, если не может открыть HTTP listener.
  Устраните конфликт порта до следующего запуска.
- **Нет доступа к Telegram.** В журнале приложения найдите `startup notification`.
  Ошибка содержит причину HTTP-запроса или ответа API, но не Bot token.
- **Telegram вернул ошибку.** Отправка проверяет не только HTTP-статус, но и JSON-поле `ok`.
  Сообщения `chat not found`, `Unauthorized` и другие причины отображаются в журнале.
- **Превышен лимит Telegram.** Для ответа `429` журнал показывает `retry_after`, если API его возвращает.
  Приложение не повторяет стартовую отправку автоматически.
- **Процесс завершён во время отправки.** Контекст запроса отменяется при остановке сервера;
  отправитель завершается до закрытия локальной БД.
- **Есть сообщение о запуске, но сайт недоступен.** Проверьте reverse proxy, Cloudflare Access,
  внешний домен и health endpoint отдельно: успешный запуск процесса их не проверяет.

API описан в [документации Telegram Bot API](https://core.telegram.org/bots/api#sendmessage).
