# Инструкции для OpenCode

## Быстрый старт

- Работай из корня репозитория `/Users/rooty/work/rooty/ai-test`.
- Модуль — `snippetbook`, требуется Go `1.27.1`.
- Установить зависимости: `go mod download`.
- Запустить приложение: `go run .`.
- SnippetBook открывается на `http://localhost:8080/`, Uptime Board — на `http://localhost:8080/uptime`.
- `PORT` задаёт порт и по умолчанию равен `8080`.
- `DB_PATH` задаёт SQLite-файл; без него используется `./app.db` в текущем каталоге запуска.

## Проверки

Запускай после изменений Go-кода:

```bash
gofmt -w .
go test ./...
go vet ./...
go build ./...
```

- Все тесты: `go test ./...`.
- Тесты конкретного пакета: `go test ./internal/monitor/...` или `go test ./internal/store/...`.
- JavaScript Ops Board проверяй командой `node --check web/ops.js`.
- HTTP-тесты могут использовать `httptest.Server`; тесты базы должны использовать отдельный путь или `:memory:`.

## Архитектура

- `main.go` создаёт store и vault, заполняет настройки, запускает Gin-сервер и background monitor.
- `internal/config` загружает `.env` и читает технические параметры `PORT` и `DB_PATH`; Cloudflare
  Access использует `CLOUDFLARE_ACCESS_TEAM_DOMAIN` и `CLOUDFLARE_ACCESS_AUDIENCE`.
- `internal/store` содержит SQLite-доступ и инициализацию схемы; `internal/model` — структуры данных.
- `internal/crypto` хранит локальный AES-GCM ключ в таблице `meta`; авторизации и vault lock нет.
- `internal/handler` содержит API и маршрутизацию; `internal/monitor` — общий protocol-neutral checker и worker.
- `web/` — vanilla JS SPA без сборщика; сервер использует файлы относительно текущего каталога.
- SnippetBook работает на `/`, Uptime Board — на `/uptime`; API находится под `/api/v1`.

## SQLite и схема

- Используется pure-Go драйвер `modernc.org/sqlite`; в `store.New()` установлен один connection.
- Новую схему добавляй идемпотентно через `CREATE TABLE IF NOT EXISTS`; старые колонки — через `ensureColumn`.
- При добавлении колонок обновляй все соответствующие `SELECT` и scan-функции.
- Все пользовательские значения в SQL передавай параметрами через `?`; не конкатенируй SQL.
- Не оставляй открытый `rows` перед следующим запросом: при одном SQLite connection это вызывает блокировки.
- Записи SnippetBook удаляются через soft delete; сервисы Ops Board сейчас удаляются физически.
- FTS5 создаётся best-effort; поиск должен иметь рабочий fallback через `LIKE`.
- Не коммить `*.db`, `*.sqlite`, `.env` и секреты.

## Ops Board

- Сервисы и результаты проверок хранятся в таблицах `services` и `service_checks`.
- `2xx`/`3xx` — `online`, `4xx`/`5xx` — `degraded`, сетевые ошибки и timeout — `offline`.
- Мониторинг проверяет только включённые сервисы и получает настройки из `app_settings`.
- Интервал задаётся у каждого сервиса в `services.check_interval`; default — `30s`. Timeout и лимит
  истории задаются через UI `/uptime` и API `/api/v1/settings`.
- `EnsureSettings()` при старте только добавляет отсутствующие defaults (`30s`, `10s`, `500`) и не
  перезаписывает значения пользователя.
- Worker выполняет due-проверки по отдельным интервалам, первая проверка включённого сервиса выполняется сразу.
- После создания сервиса handler запускает первую проверку синхронно и возвращает `last_check` в ответе.
- Повторные уведомления настраиваются у сервиса (`repeat_notifications_enabled`,
  `repeat_notification_interval`), default выключен; начало и восстановление инцидента уведомляются всегда.
- Уведомления глобальные для всех сервисов: `internal/notify` отправляет status-change event в
  включённые Telegram, Slack и SMTP каналы; конфигурация хранится в `app_settings`.

## Требования к диагностике проверок

- Для **каждой проверки на всех сервисах** общий статус недостаточен: при любом `warning`, `error`,
  `offline`, `degraded`, `tls_error` или `not_found` интерфейс обязан показывать максимально подробную
  диагностическую информацию.
- Диагностика должна указывать конкретный объект, на котором сработала проверка: URL или endpoint,
  hostname, порт, IP-адрес, DNS-запись, имя DNSBL/RBL, DKIM selector, MX priority или другой применимый
  идентификатор.
- Для сетевых проверок показывай этап и причину сбоя: DNS lookup, TCP connect, TLS handshake,
  certificate validation, SMTP/IMAP/POP3 command, HTTP status, response error или timeout.
- Для TLS обязательно показывай статус сертификата, hostname, issuer, дату окончания действия,
  оставшееся количество дней и текст ошибки проверки, если сертификат не прошёл проверку.
- Для Mail Diagnostics показывай исходные диагностические детали всех секций: найденные MX и IP,
  SPF-запись и lookup count, DKIM selector и наличие public key, DMARC policy и параметры, а для
  DNSBL/RBL — конкретный IP, список, результат и ошибку запроса.
- Если проверка сработала и уменьшила score, явно показывай название проверки, её статус, причину,
  применённый штраф и итоговый расчёт. Нельзя ограничиваться только цветом или числом score.
- Сохраняй диагностические поля в API и истории проверки, чтобы подробности были доступны после
  повторного открытия результата, а не только во время выполнения запроса.
- При добавлении нового протокола или проверки одновременно добавляй: подробное поле ошибки в модели,
  отображение в UI, сохранение в истории и тест, проверяющий диагностический результат.

## Маршрутизация и фронтенд

- Не используй `r.Static("/", "./web")`: это конфликтует с `/api`.
- Статические файлы подключаются явными маршрутами, а `NoRoute` оставляет SPA fallback.
- После изменения Ops Board проверяй и `web/ops.js`, и соответствующий API-контракт.
- Сохраняй SnippetBook и его маршруты при любых изменениях Ops Board.

## Завершение изменений

- После завершения полной задачи обязательно выполни проверки проекта, создай коммит с понятным
  сообщением, объедини изменения в `main` и отправь результат в `origin/main`.
- Не включай в коммит локальные базы данных, `.env`, секреты и личные скрипты, если они не относятся
  к задаче.
- Если среда блокирует `git push`, явно сообщи об этом и укажи созданный коммит и команду для повторной
  отправки.

## Документация и границы задачи

- Документация проекта пишется на русском языке.
- Не добавляй без отдельного запроса shell-команды, Kubernetes, cloud sync, multi-user или
  автоматический restart. SSL checks, runbooks, reminders и browser notifications уже входят в Ops Board.
